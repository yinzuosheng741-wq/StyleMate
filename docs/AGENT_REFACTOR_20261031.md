# Agent 执行契约优化与可行性判断

日期：2026-10-31。范围：任务路由、三个现有 Skill、工具执行与评测口径。

## 方向判断

当前适合定位为面向衣橱与出行的单 Agent 应用框架。业务规则、RAG、工具权限和桌面客户端已有实际价值；继续增加框架名称或 Agent 数量无法直接解决目前的执行差异。

| 方向 | 收益与可行性 | 本轮处理 |
| --- | --- | --- |
| 统一任务判定 | 分散关键词规则会造成入口行为与工具可见性不一致，改造成本可控 | 实现统一意图判定与路由结果，服务、图复用；旅行续问从所属会话补充上下文 |
| 统一领域执行 | 桌面与对话各自处理偏好、候选库存，容易产生差异 | 穿搭工具改为调用桌面相同的 OutfitPlanningSkill |
| Skill 契约真正执行 | 原有 spec 主要是说明，限制 trace 长度不能阻止动作 | 三个 Skill 均接入 SkillRun，在动作开始前检查名称及步骤预算，并验证输入、输出 |
| 区分调用与业务结果 | 正常返回未找到、追问和空组合，也可能被统计为成功 | 保留执行状态，增加业务 outcome、原因、可重试性和缺失条件，传入模型上下文 |
| 全工具强类型输出 | 有收益，但一次性改动所有领域输出风险较大 | 先覆盖准确衣物查询与库存穿搭；其余工具保留数据结构，统一结果元信息 |
| 多 Agent、长任务恢复 | 当前主要是几步以内桌面任务，收益尚无证据 | 暂缓；当前会话持久化仍不等同于中途执行恢复 |

架构选择参考 [LangGraph 官方 Workflows and agents](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/workflows-agents.mdx)：固定业务流程与模型自主编排适合承担不同职责。本项目保留确定性流程和有界模型工具循环，未更换底层框架或引入新依赖。

## 实现与边界

`agent/routing.py` 统一输出 `intent`、适用领域、可用工具、确定性执行标志及洗护追问。中文口语穿搭请求使用一组有限的表达规则补充识别。路由领域标签仍有五类，实际领域 Skill 有三个，二者不宣称一一对应。准确衣物解析、所有权验证、旅行参数抽取及确认写入仍由各自业务边界负责。

`skills/runtime.py` 为每次调用建立独立执行状态。三个 Skill 的动作必须先通过白名单与次数检查，再进入动作体；输入重新校验，输出按声明模型校验，追踪记录真实经过时间及有限状态，不记录图片、用户备注或异常正文。知识检索最多两次 search；衣物识别最多两次视觉请求。

步骤预算约束的是领域动作，不是线程强制终止或 HTTP 请求数。例如知识改写动作包含第二次检索与来源检查，视觉动作包含响应验证。同步线程超时后仍不能被 Python 安全强杀；外层 ToolExecutor 继续负责容量、等待超时与整轮截止时间。

`OutfitPlanningSkill` 统一处理当前用户偏好、候选衣物过滤及规则推荐。指定候选全部失效时返回空组合，不扩大库存范围。已提供天气条件时保留调用方条件；对话工具不隐式请求天气，天气继续作为独立工具计入调用预算。桌面可通过自己的 loader 获取天气。

另修复快捷入口的调用顺序：选中单品、歧义和未选择单品的判断先于快捷工具执行，避免未采用的快捷结果消耗工具预算。

## 工具结果约定

兼容保留 `result`、`trace` 和 `sources`，新增以下模型可见字段：

| 字段 | 含义 |
| --- | --- |
| `execution_status` | 处理器是否正常执行：success / fallback / failed |
| `outcome` | 业务结果：success / empty / not_found / needs_clarification / unavailable / error |
| `reason_code` | 有限的结果或错误原因代码 |
| `missing_conditions` | 需要向用户补问的条件 |
| `retryable` | 是否允许稍后重试；不代表必须自动重复请求 |

例如准确查询不存在的衣物：执行成功，但业务结果是 `not_found`。未知材质洗护与缺少购买条件：执行成功，业务结果是 `needs_clarification`。模型提示明确要求按业务结果回答。

准确衣物查询验证 found 与 garment 的一致性；库存搭配验证完整 OutfitRecommendation 结构与数量。无效结构停止展示。其他工具的数据内容尚未全部迁移成领域专用输出模型，不把元信息统一误称为所有数据均已强类型化。

诊断 schema 升为 2，在已有处理器执行计数之外增加只读工具各 outcome 计数；评测报告单独保存 `read_tool_business_outcomes`。该统计不包括写操作准备和在处理器前就被拒绝的请求。正常追问可以满足用户任务验收，但不会因此被算成业务结果 success。

## 验证记录

新增边界测试覆盖：执行前拦截越权与超预算动作、三个真实 Skill 的预算生效、非法输入与输出、桌面/工具穿搭一致性、失效候选不扩容、天气不重复请求、结果状态传入模型、未找到与追问分开计数、选中衣物时不执行无用快捷调用。

沿用原回归与 v2 题目、标签、语料及质量门槛，没有通过放宽期望提高结果。v2 已作为优化回归资料使用，本轮结果不是独立盲测；下一批泛化验证应先冻结新问题，再开始相关规则优化。

| 已有 v2 回归指标 | 上轮 | 本轮 |
| --- | ---: | ---: |
| 功能验收 | 147/150，98% | 150/150，100% |
| 预期工具命中 | 117/120，97.5% | 120/120，100% |
| 工具集合完全一致 | 132/150，88% | 132/150，88% |
| 库存保持不变 | 150/150 | 150/150 |

重复三次仍然只有 50 个独立场景。100% 不能推广成真实用户任务完成率；工具集合完全一致没有提高，不能声称路由全面达到 100%。已有天气故障注入场景正常产生工具失败，故处理器成功率也不是 100%。

原始结果：[v2 报告](../artifacts/benchmark-20261031-framework-v2.json)、[真实模型链路报告](../artifacts/benchmark-20261031-framework-live.json)、[完整验证与构建核验摘要](../artifacts/framework-release-20261031.json)。三份结果的源码指纹一致；原题、语料和模型设置与上轮逐项核对一致。本轮模型上下文新增了结果元信息及相关提示，因此指标反映整个改动组合，不能归因于某一个模块。

完整检查 **512 项测试通过**，较上轮增加 20 项；Agent 代码行覆盖约 **93%**。依赖、锁定约束、健康检查、素材审计、Ruff、编译和原历史质量门槛全部通过，验证期间源码指纹未变。覆盖率只描述离线执行路径，不是功能准确率。

20 次中有 2 次未知材质追问由前置规则完成，其余 18 次调用真实模型。模型输出仍可能额外调用工具；控制台的 fail 也包含工具集合不完全相同，不能直接解释为功能失败。单品名称复述的既有文本验收本次通过，但没有修改原标签。

延迟是小样本观测，P99 本轮反而更高，不能承诺稳定提速或把平均耗时下降解释成模型本身加速。新统计的 30 次只读处理器结果分别是 26 次 success、2 次 needs_clarification 和 2 次 unavailable；另有 2 次写操作准备，合计 32 次工具执行未失败。不要把 32/32 解释为 32 次都找到了业务结果。

原 20 条有答案检索题的真实混合 Recall@5 仍为 95%，4 条无答案题均拒答；本轮没有更改检索实现。SQLite 隔离 CRUD 检查沿用原口径。连接探针测试的是本次配置响应，不是服务可用率。

Windows 公开 ZIP 完整性及解压后 `--no-ui` 启动通过，检查未包含个人数据库与私有配置。本机自用客户端已更新并启动，窗口响应正常；更新前后 **134 个个人数据文件哈希一致**。界面未在本轮改版，窗口响应检查不等同于逐页面人工验收。

## 后续优先级

1. 冻结独立测试问题并进行人工相关性、回答支持性标注，覆盖同义表达、混合任务、否定和多轮改口。
2. 按业务风险逐步补齐其余工具的专用输出模型；评测分别看执行、业务结果和最终回答验收。
3. 只有出现可复现的长任务需求后，再加入执行恢复；有独立并行任务收益后再考虑多 Agent。
